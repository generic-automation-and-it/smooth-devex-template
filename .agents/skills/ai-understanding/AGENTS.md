# ai-understanding — AGENTS.md

## TL;DR

An Understanding is the input and outcome of a session's memory, written for another agent to act on — reusable, terse, structured, and holding only what no code file or knowledge document already holds. `--export` writes them to `<subject>/<slug>.md` files under the gitignored `.context/understandings/`; the store is disposable by design, so `--publish` is the only path by which knowledge leaves a workspace — never weaken the `scope` gate that governs it.

## Non-Negotiables

- **Never drop the subject folder.** `<subject>/<slug>.md`. The subject is what keeps a session's lessons legible as a body of work months later, and it was an explicit design correction from the user — not an incidental layout choice. Equally, do not reintroduce a folder per unit: a unit is one file, and the rare unit carrying artifacts puts them in a sibling `<slug>.assets/`.
- **Never make the index subject-first for retrieval.** The index groups by subject for browsing, but lists every unit with its question, because an agent has a question in mind rather than a subject. An edit that makes a reader open a subject before seeing questions files knowledge under the one label nobody searches by.
- **Never let a write overwrite an existing slug.** Merge on a matching question, disambiguate otherwise. An edit that adds an "overwrite" or "force" path deletes knowledge the user chose to keep.
- **Never let `--portable-only` publish a `repo-specific` unit.** That filter is the only thing preventing a local quirk from being shipped to another repo with provenance that makes it look universally verified.
- **Never add remote fetching to this skill.** Remote consumption routes through `ai-asset-sync`'s manifest. Two transport implementations means two provenance models and two merge semantics.

## Architecture Decisions

### LADR-001 — Working store is local and disposable; publish is the durability boundary

- **Date:** 2026-09-19 · **Status:** Accepted
- **Context:** Understandings could live in a tracked path (`.agents/understandings/`, syncable immediately) or in the gitignored `.context/` tree. A tracked store makes every encoded unit instantly shareable — and instantly permanent. Most of what a session produces is not worth keeping, and review pressure at encode time is exactly when the knowledge is least settled.
- **Decision:** The working store is `.context/understandings/` (local, gitignored, per-workspace) and `--export` writes the session's knowledge there. Reaching a tracked path is a separate, human-approved `--publish` step, with `.agents/understandings/` as the default destination.
- **Consequences:** Encoding stays cheap and low-stakes, so agents propose freely. Review happens once, at publish, when it is clear which knowledge held up. Trade-off: a workspace destroyed before its publish loses its memory — accepted, because the alternative pollutes shared memory with unreviewed observations. The tracked destination is created on first publish; nothing is seeded, so a repo that never publishes carries no empty scaffolding.

### LADR-002 — `scope` is a first-class field, not a judgment made at publish time

- **Date:** 2026-09-19 · **Status:** Accepted
- **Context:** Deciding portability when publishing means judging units long after the session that produced them, with none of the context that would reveal whether a behavior was general or an artifact of this repo's setup.
- **Decision:** Every Understanding declares `scope: portable | repo-specific` at export time, while the evidence is fresh. Publish filters on the field rather than re-deciding.
- **Consequences:** Publishing is mechanical and auditable. The judgment sits where the information is. Bias toward `repo-specific` when unclear: leaving knowledge behind costs one rediscovery, while publishing a false universal costs every consumer that acts on it.

### LADR-003 — `INDEX.md` is generated, and is a reference table only

- **Date:** 2026-09-19 · **Status:** Accepted
- **Context:** An index maintained by hand drifts from the units, and an index that inlines the knowledge defeats its own purpose — an agent that must read the whole index to find one applicable Understanding has already paid the tokens it was trying to save.
- **Decision:** `scripts/understanding_index.py` regenerates `INDEX.md` from frontmatter. Rows carry unit, description, question, scope, confidence, updated — reference data for matching, never the knowledge itself. `question` lives in frontmatter only, so the index cannot contradict the unit.
- **Consequences:** Importing is a two-step read: match questions in the index, then open only matching units. The script validates as it goes (required fields, slug/folder agreement, enum values, store-wide slug uniqueness, dangling `[[links]]`, and units left at the old single-level depth) and exits `1` on problems while still writing the index, so drift surfaces without blocking the write. There is no INDEX template — the generator is the single source.

### LADR-004 — Subject folder groups; the question still retrieves

- **Date:** 2026-09-19 · **Status:** Accepted
- **Context:** A session usually has one main subject, and splitting its lessons into sibling top-level folders loses that — the work reads as five unrelated facts a month later. The obvious fix, making the subject the addressable unit with several Understandings inside it, breaks two things: retrieval (most of what a session teaches applies to work that has nothing to do with the session's subject) and publish granularity (one subject folder routinely mixes `portable` and `repo-specific` units, so it cannot be moved wholesale).
- **Decision:** `<subject>/<slug>.md`. The subject folder groups for browsing; the file stays the addressable unit for retrieval, merging, `[[links]]`, scope filtering, and confidence. The generated index groups by subject but lists every unit with its question. Slugs are unique store-wide, so a link or a merge never needs to name the subject.
- **Consequences:** A session stays legible as a body of work without knowledge becoming findable only through its origin. Cost: every Understanding needs a subject (`_unfiled/` absorbs the ones with no topic). Units left in an older layout — at the store root, or in a per-unit folder — are reported as a problem naming the fix rather than silently skipped.
- **Superseded sub-decision:** the unit was first a folder (`<slug>/UNDERSTANDING.md`) to namespace evidence artifacts. That cost a directory level on every unit to serve a case that had not occurred in any of the first five, all of which quote their evidence inline. The unit is now a file; artifacts, when a unit genuinely has them, go in a sibling `<slug>.assets/` whose name derives from the slug and so cannot collide. The rejected objection — that publishing would have to "reach inside" a subject folder — was wrong: the file is the unit, so per-unit publish is a file copy.

### LADR-005 — Record inherited lineage, not the session's reasoning

- **Date:** 2026-09-19 · **Status:** Accepted
- **Context:** Import wrote nothing back, so the store had no evidence of which knowledge was ever used — a unit nothing inherits is indistinguishable from one that simply has not come up, which makes pruning guesswork and leaves no blast radius when a unit turns out wrong. A proposed alternative modelled the export on the novel's generational framing with four dimensions per unit: inherited knowledge, the conflict encountered, the cost-benefit reasoning behind the agent's adaptation, and the resulting lesson.
- **Decision:** Take the lineage only. `provenance.inherited` lists the `[[slug]]`s a session loaded **and acted on**. The other three dimensions are rejected: "the conflict encountered" and "the reasoning behind the adaptation" are agent-centric — they record what the agent did and why it adapted, which is a session log with better vocabulary — and "the resulting lesson" is the Understanding itself under another name.
- **Consequences:** One optional list buys a usage signal, a lineage graph, and the ability to find what depended on a unit later found wrong. The store stays knowledge-centric: what is true and when it applies, never the journey that produced it. A bracketed entry must resolve; unbracketing records an ancestor that has since been pruned or promoted, so removing a unit does not either break the index permanently or force rewriting history. Not adopted: machine-validating the *quality* of recorded reasoning — a checker can only confirm a field is non-empty, which teaches agents to write filler into a required box.

### LADR-006 — Publish defaults to every unit; `--portable-only` filters for the cross-repo case

- **Date:** 2026-09-19 · **Status:** Accepted
- **Context:** The original default (`--publish` = `scope: portable` only, `--all` for the rest) was tuned for cross-repo publishing when the common case is same-repo team sharing — handing a teammate the memory for the repo they already work on. Measured on a real store of 8 units: `--publish` produced 1 unit, 2.1 KB; the same store with `--all` produced 8 units, 16 KB. Everything about the repo's own build, CI and tooling — the part a teammate most needs — was filtered out by default, and the common operation required a flag while the rare one was free.
- **Decision:** `--publish` archives **every** unit by default. `--portable-only` restricts the archive to `scope: portable` units, for the case where the destination is another repository. `--all` is retired from publish; it keeps its distinct, unrelated meaning on `--export` (skip the pre-write cut).
- **Consequences:** A same-team archive is complete by default — the common operation needs no flag. Cross-repo publishing now requires remembering `--portable-only`, and forgetting it ships `repo-specific` knowledge elsewhere — which is why the guardrail above moves to attach to `--portable-only` rather than disappearing. `scope` (LADR-002) is unaffected: it is still declared at export time and is still the only thing `--portable-only` filters on. Filtering a subset also means a published unit's `[[link]]` can point outside the archive; the zip-publish worktask carries the fix (drop the brackets, keep the entry) as a consequence of this decision. **Rejected alternative:** keep `portable-only` as the default and require `--all` for the complete case — rejected because it optimizes for the rarer cross-repo operation at the cost of the common same-repo one.

## Key Behaviors

- **"Understanding" is a term of art, borrowed from Adrian Tchaikovsky's _Children of Time_.** In the novel an Understanding is knowledge distilled and passed to a generation that never had the experience which produced it — which is exactly the contract here: the originating session is discarded, the transferable knowledge survives. Do not "clarify" the name to `learnings`, `notes`, `lessons`, or `memories`. Those all invite session logs; this one does not, and the distinction between a log and an Understanding is the whole design.
- **A unit is a question and its answer, not a topic and some notes.** Frontmatter carries the `question` a reader has at the moment the knowledge applies; the body's `## Answer` addresses that and nothing wider. The pairing is a constraint, not a format: one question has one answer, so an answer that outgrows its question means the question was too narrow, and a question no answer covers means it was too broad. This replaced a situation-shaped `trigger` field, which could sprawl — the eval rounds found exactly that defect, a trigger matching cases its own body could not answer.
- **`provenance.inherited` is read back, and that is the point of it.** `--review` computes which units nothing has ever inherited and flags them: the question probably does not match what anyone asks. LADR-005 justified the field as a usage signal, and for several rounds it was decorative — validated on write, never read. An edit that stops writing it, or stops `--review` reading it, removes the only evidence the store has about its own worth. The signal self-suppresses in a store where no unit records inheritance yet, so a young store is not flooded with false positives.
- **Decay is advisory, never a validation failure.** A contested, unused or overdue unit is not *wrong*, so `--review` prints and exits `0`. Folding decay into the problem list would train agents to ignore the problem list, which is where real defects are reported.
- **Outcomes are a first-class kind of unit, and the only kind with no `*AGENTS.md` fallback.** What a piece of work produced — requirements distilled from meetings, the issues and PRs it opened and their state, what was specified but left unbuilt — is knowledge a next session needs first and that no context document carries, because an `*AGENTS.md` records what the code does rather than what is still owed. The ban on session logs is about **shape**: a narrative of the work is out, the durable artifacts and their state are in. These units go stale fastest, so each carries its date and the command that re-checks it.
- **The store is for the product, not the process.** An Understanding carries functional and non-functional knowledge about the system being built; knowledge about the agent toolchain that produced it — a skill's internals, a scanner's dependencies, a workflow's trigger filters — belongs in the nearest `*AGENTS.md`. This was learned the expensive way: the store accumulated eight units across ten eval rounds, and on review six were plumbing about the repo's own skills. Effort spent learning something does not qualify it; a toolchain quirk can cost an afternoon and still not be memory about the product.
- **Understandings are evidence; rules are orders.** The governance half of this design lives in `.github/instructions/meta/understandings.instructions.md`, not here, because importing must work at session start without anyone invoking the skill. Editing one side without the other splits the contract.
- **A session splits into several slugs inside one subject.** One Understanding per question, each standing alone, grouped under the subject it came out of. Merging a session's lessons into one unit to keep the count down produces a unit whose question matches everything and therefore nothing — the subject folder is what keeps them together, not a shared file.
- **Consumed units land as `confidence: observed`,** whatever they claimed at the source. They were verified against a setup that may differ.
- **A `verified` unit is not a correct unit.** Two independent agents asked to check one against the code found a false claim in it — the unit asserted a behavior that reading the source disproves. `confidence` records how the knowledge was obtained, not that it is right, which is why the import protocol tells agents to verify rather than defer. An edit that softens that instruction removes the only mechanism that catches this.
- **Promoted knowledge does not stay in the store.** Once an Understanding is folded into a `*AGENTS.md` or a rule, the store copy is a competing copy that will drift. The naming-vocabulary lesson recorded above in Key Behaviors was exported as a unit first and then removed for exactly this reason.
- **Promotion is the exit, not a cleanup chore.** An Understanding proven across many tasks belongs in a `*AGENTS.md` or a rule, which load without a skill invocation. Leaving it in the disposable store means re-earning it every workspace.
- **Export/import are session↔disk; publish/consume are repo↔repo.** The first naming made `--export` mean "copy to a tracked path", which reads as publishing to anyone who thinks of export as getting a session's memory out of the conversation — the switch did not do what its name promised, and the mode was invoked expecting analysis. Do not collapse the two pairs back together.
- **The frontmatter parser is hand-rolled** because PyYAML is not available in this environment. It handles flat scalars, top-level lists, a nested map, and a list inside that map (`provenance.inherited`) — and nothing deeper. Adding a frontmatter field with more structure means extending `parse_frontmatter`, not just the template; the `inherited` list was exactly that case and the naive version silently clobbered the whole `provenance` map into a list.
- **Reference validation is generic; parsing is the narrower constraint.** Any frontmatter list — top-level, or one level inside a map — has its `[[slug]]` entries resolved by `dangling_references`, so a field added to the template is checked without touching the generator. Only bracketed entries are references; a bare string is a historical note, which is how `provenance.inherited` survives naming an Understanding that was later pruned or promoted. What still needs a code change is a field with a *shape* the parser does not handle — and the shape that bites is not only the deep one. A list written in YAML flow style (`links: [[a]]`) parses as a plain **scalar**, never reaches the walk, and used to let a dangling reference exit `0`; it is now reported as its own problem naming the block form, rather than the parser guessing whether `[[a]]` is one reference or a nested sequence. Validation used to be per-field (`dangling_links` and `dangling_inherited`, each by name), which let a dangling reference in an unrecognised field exit `0`; the two walkers were merged once the second one proved the case. The parser reads **block lists only**; a flow-style list (`links: [[a]]`) becomes a scalar and is invisible to the reference walk, so `inline_sequences` names that shape as a problem rather than silently passing it. Two traps when touching it: the check must cover a flow sequence **nested in a map** (`provenance.inherited`) as well as a top-level one — fixing only the top level repeats the per-field mistake one level up — and it must require the closing `]`, or a description reading `[draft] …` is reported as a list.

## Test References

No automated tests. The generator's validation paths (missing/placeholder `description`/`question`/`scope`/`confidence`/`updated`/`provenance.*`, slug-vs-folder mismatch, invalid `scope`/`confidence`, a non-existent `agents_context` path, a slug not matching its file name, duplicate slugs across subjects, dangling `[[slug]]` references in a top-level list, in `provenance.inherited`, and in a field the generator has never heard of, a unit left in the old per-unit-folder shape, a unit stranded at the store root, an empty subject folder, dangling links and dangling `inherited` entries, empty store, absent store) its lineage validation (resolving, dangling, and deliberately unbracketed `provenance.inherited` entries), a list written in YAML flow style rather than block style, its flow-sequence detection (top-level, nested in a map, block form, and prose beginning with `[`), the `--review` report (inherited vs orphaned, contested, and both staleness thresholds), and its argument handling (`--help`, `--review`, unknown flag, surplus argument) were exercised manually against fixtures. `parse_frontmatter` additionally has direct assertions for the nested-list case, same-indent list items, a scalar following a list, and absent frontmatter. A fixture carrying dangling references in both `links` and an unrecognised sibling list (`supersedes`) confirms the generic walk described in Key Behaviors: **both** are reported, and removing the `links` dangler still exits `1` on the unrecognised one. That fixture was written when validation was per-field and the second dangler escaped with exit `0`; it is kept because it is the regression test for that gap. Re-run them after touching `parse_frontmatter` — the list-under-key branch in particular is easy to break in a way that silently drops `links` instead of erroring.
